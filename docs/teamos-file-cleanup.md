# TeamOS project file cleanup

The Android client records all project file paths before deleting the project row. The record survives the project cascade. After deletion, both the client and the server worker can remove the Storage objects and then delete the cleanup record. Failed deletions leave the record for retry. The worker skips records whose project still exists.

Deploy `202611250001_teamos_file_storage.sql` and `202611250002_team_file_cleanup.sql` before shipping the Android change. Deploy the `mentor-team-cleanup` Edge Function with JWT verification enabled. Set `TEAM_CLEANUP_SECRET` to a random secret; keep it outside Git. Supabase supplies `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` to the function. Invoke `POST /functions/v1/mentor-team-cleanup` on a trusted server schedule with both a valid service-role JWT in the `Authorization` header and `x-team-cleanup-secret`. A successful response contains `completed` and `failed`; HTTP 503 means at least one record remains for retry. Never place either secret in the Android app.

The schedule is project configuration, not a migration: the project URL and Vault secrets differ between environments. Enable `pg_cron` and `pg_net`, put an anon JWT and a separate random cleanup secret in Vault, then schedule the function every 10 minutes. Keep the same cleanup secret in the Edge Function environment. Never use a service-role key as the schedule's JWT; the function already has its own server-side service-role key. Monitor `cron.job_run_details`, `net._http_response`, and the remaining row count in `public.mentor_team_file_cleanup`. An old app version that deletes projects without creating cleanup records cannot be repaired retroactively by this worker.

Production deployment evidence for project `hnxphwuaccztzanjcuca` on 25 November 2026: migrations `202611250001` and `202611250002` were applied; `mentor-team-cleanup` was deployed with JWT verification enabled; Vault secrets and active cron job `mentor-team-file-cleanup` (`*/10 * * * *`) were configured. A manual invocation through `pg_net` returned HTTP 200 with `{"completed":0,"failed":0}`. The first scheduled run also succeeded and its HTTP response was 200. The cleanup table had zero pending jobs, so deletion of a real Storage file has not been tested on production. No production data was created as a fixture.

Rollback: stop the scheduler and redeploy the previous app. Keep the cleanup table and Storage policies while any cleanup records remain; removing them early would strand files. The migration does not delete existing user data.
